# Project: Reliable API Data Ingestion Pipeline

Act as a senior data engineer and coding mentor. Build a complete, runnable, well-tested Data Engineering project for a 72-hour Associate AI Forward Deployed Engineer coding challenge.

## 1. Core objective

Implement a reliable API ingestion pipeline that consumes paginated API data and handles:

- Configurable authentication.
- Rate limiting and HTTP 429 responses.
- Transient network errors and server errors.
- Exponential backoff and retry limits.
- Incremental checkpoints and restart recovery.
- Raw API response retention.
- Schema and business-rule validation.
- Duplicate handling and referential integrity.
- Rejected-record quarantine with traceable reasons.
- Idempotent target publishing.
- Run-level operational metrics and structured logging.
- Reproducible mock API behavior.
- Automated tests and measurable performance.

Build a complete vertical slice. Prioritize correctness, simplicity, maintainability, reproducibility and honest validation over unnecessary complexity.

## 2. Technology stack

Use:
- Python 3.11 or newer.
- FastAPI and Uvicorn for the local mock source API.
- Requests for HTTP ingestion.
- Pydantic for configuration and schema validation where appropriate.
- SQLite for durable target data, run metadata and checkpoints.
- JSON Lines or JSON files for raw-response retention and quarantine.
- Pytest for automated tests.
- Standard Python logging and timing utilities.
- Faker only if needed for scalable synthetic data generation.

Pin compatible dependencies in requirements.txt. Avoid Docker, cloud services, paid APIs and external credentials unless genuinely necessary.

Check the installed Python version and available environment before choosing commands. Do not claim that a command succeeded unless you actually ran it and observed the result.

## 3. Domain and data model

Use a realistic synthetic business domain: customer orders.

Define these entities:

1. customers
   - customer_id: stable string primary key
   - name: required non-empty string
   - email: required valid email
   - created_at: ISO-8601 UTC timestamp

2. orders
   - order_id: stable string primary key
   - customer_id: required foreign key to customers
   - amount: decimal-compatible non-negative monetary value
   - currency: three-letter currency code
   - status: constrained set of order states
   - updated_at: ISO-8601 UTC timestamp
   - source_event_id: stable source event identifier
   - source_page or source cursor where appropriate
   - ingestion_run_id: identifier for the processing run

Document record grain, keys, nullability, constraints, relationships, assumptions and derived fields.

Include an event or audit history for meaningful changes rather than silently discarding change history. Clearly distinguish event-level uniqueness from current-state order uniqueness.

Use deterministic synthetic IDs and a fixed random seed. Keep any expected-answer labels separate from source input records.

## 5. Mock API requirements

Build a local FastAPI service with endpoints for paginated customer and order records.

Support:
- Page-based pagination or cursor-based pagination, documented clearly.
- Configurable page size.
- Synthetic dataset generation.
- Optional bearer-token authentication with a configurable local test token.
- HTTP 429 responses with Retry-After.
- Temporary HTTP 500 failures.
- Simulated timeout or connection failure where practical.
- Malformed records and missing fields.
- Duplicate source records.
- Unexpected schema fields.
- Late-arriving or out-of-order events.
- Empty result sets.
- Deterministic fault injection for repeatable tests.

Fault injection must be configurable and deterministic. Provide a normal mode that succeeds and explicit scenarios that trigger failures. Do not make the normal run randomly fail.

Never embed real secrets. Use dummy credentials only in tests and document the environment-variable configuration.

## 6. Ingestion engine

Implement readable, typed functions with useful docstrings.

Requirements:
- Fetch all pages until completion.
- Handle network exceptions, HTTP 429 and retryable 5xx responses.
- Respect Retry-After where provided.
- Use configurable exponential backoff and a maximum retry count.
- Avoid retrying permanent client errors unnecessarily.
- Validate responses and detect unexpected schemas.
- Persist each raw API response before processing it further.
- Preserve enough metadata to trace each record to its original response, page/cursor and run.
- Use a durable checkpoint with clear semantics.
- Advance the checkpoint only after the corresponding page has been durably handled.
- Ensure partial failure and restart do not silently skip records.
- Make retries and repeated runs safe.
- Support incremental ingestion and a documented backfill mode.
- Make the page size, request timeout, retry count, paths and database configurable.
- Separate transport, validation, transformation, storage and reporting logic.

Do not pretend page-number checkpoints guarantee correctness if the upstream source can change between page requests. Explain the limitation and use a stable cursor or deterministic mock source when appropriate.

## 7. Validation and transformation

Implement deterministic validation rules.

At minimum, reject:
- Malformed JSON.
- Missing required fields.
- Null or invalid primary keys.
- Invalid email addresses.
- Negative amounts.
- Invalid timestamps.
- Unsupported currency or status values.
- Orders referencing nonexistent customers.
- Invalid source event IDs.

Handle duplicates using explicit documented policies:
- Exact duplicate source events should not create duplicate target rows.
- Conflicting records with the same event ID must be detected and quarantined or reported.
- Repeated order IDs with newer legitimate events should follow a documented current-state and history policy.

Quarantine records with:
- Original record or raw-response reference.
- Run ID.
- Source page/cursor.
- Rejection reason and validation error.
- Processing timestamp.

Do not silently drop invalid records. Separate record-level data-quality errors from fatal pipeline errors.

Unexpected schema changes must be observable and handled according to an explicit policy.

## 8. Storage and idempotency

Use SQLite with appropriate primary keys, foreign keys, indexes and transactions.

Create tables for:
- customers
- orders
- order_events or equivalent change history
- ingestion_runs
- checkpoints
- quarantined_records or a durable quarantine manifest

Include stable run IDs, UTC start/end timestamps, status, pages fetched, raw records received, accepted records, inserted/updated records, duplicates, rejected records, retry counts, elapsed time and failure details.

Use atomic transactions for target writes and checkpoint advancement where feasible. Explain any boundary between file writes and database transactions and how recovery handles it.

Rerunning the same input must not create unintended duplicate target records or duplicate logical events.

Support a clean reset for test/demo purposes, with a clear warning before destructive actions.
